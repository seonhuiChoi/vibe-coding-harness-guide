바이브 코딩이 뭔가요

코드를 직접 타이핑하는 대신, 만들고 싶은 것을 우리말로 설명하면 AI가 코드를 써주는 방식입니다. 문법을 외우는 능력 대신 원하는 걸 정확히 설명하는 능력이 실력이 됩니다.

2025년 2월 2일 안드레이 카파시(Andrej Karpathy)가 X에 올린 짧은 글에서 이름이 붙었습니다. 코드가 있다는 사실조차 잊고 흐름에 몸을 맡기는 새로운 코딩이라는 취지였죠. 그해 콜린스 사전은 “vibe coding”을 올해의 단어로 선정했습니다.

그런데 그대로 하면 망합니다

“다 맡기고 코드는 보지도 않는다”는 원래 뜻 그대로 실무에 적용했을 때 어떤 일이 벌어지는지, 2025~2026년에 충분히 많은 사례가 쌓였습니다. 인증 처리가 빠진 API, 코드에 박힌 비밀 키, 돌아가긴 하는데 아무도 못 고치는 코드.

그래서 2026년의 흐름은 “맡기되, 틀렸을 때 자동으로 걸리게 만든다” 쪽으로 갔습니다. 이걸 하네스 엔지니어링이라고 부릅니다.

    약 20분공식 가이드 기반

    원칙 1 · 구체적으로

    클로드는 의도를 추측할 수는 있지만 마음을 읽지는 못합니다. 어느 파일인지, 어떤 상황인지, 무엇을 피해야 하는지를 넣으세요.

    ✗버그 고쳐줘
    ✓비밀번호를 틀리게 입력하면 빈 화면이 뜨는 로그인 버그를 고쳐줘
    ✗foo.py 테스트 만들어줘
    ✓foo.py에 대해 로그아웃 상태 엣지 케이스를 다루는 테스트를 써줘. 목(mock)은 쓰지 마.

    원칙 2 · 확인할 방법을 같이 주기

    다섯 중 가장 중요합니다. 클로드는 “다 된 것 같으면” 멈춥니다. 검사할 방법이 없으면 그 판단을 사람이 대신 해야 하고, 결국 모든 실수가 사용자가 발견할 때까지 방치됩니다. 반대로 스스로 돌려볼 수 있는 검사를 주면 통과할 때까지 알아서 반복합니다. 이게 트랙 3 하네스의 씨앗입니다.

    ✗이메일 검증 함수 만들어줘
    ✓이메일 검증 함수를 만들어줘. 예시 — user@example.com은 통과, invalid는 실패, user@.com은 실패. 만든 다음 테스트를 돌려서 확인해줘.
    ✗대시보드 좀 예쁘게 만들어줘
    ✓[이미지 붙여넣기] 이 디자인대로 만들어줘. 결과를 캡처해서 원본과 비교하고, 다른 점을 목록으로 뽑아서 고쳐줘.
    ✗빌드가 안 돼
    ✓빌드가 이 오류로 실패해 — [오류 붙여넣기]. 고치고 빌드가 성공하는지 확인해줘. 오류를 덮어서 숨기지 말고 근본 원인을 잡아줘.
    한 줄 요약

    “됐다”고 말하지 말고 증거를 보여달라고 하세요. 테스트 출력, 실행한 명령과 결과, 화면 캡처. 증거를 확인하는 게 직접 다시 돌려보는 것보다 훨씬 빠릅니다.

    원칙 3 · 이미 있는 것을 가리키기

    설명하지 말고 지목하세요. @파일이름 을 쓰면 클로드가 그 파일을 먼저 읽고 답합니다. 이미지는 그대로 붙여넣거나 끌어다 놓으면 됩니다.

    ✗달력 위젯 하나 추가해줘
    ✓홈 화면의 기존 위젯들이 어떻게 구현됐는지 보고 패턴을 파악해줘. HotDogWidget.php가 좋은 예야. 같은 패턴으로 달력 위젯을 만들어줘. 이미 쓰는 라이브러리 외에 새 걸 추가하지 마.

    컨텍스트 관리와 되돌리기

    고급 요령의 대부분이 여기서 나옵니다. 클로드가 갑자기 멍청해지는 것처럼 느껴지는 순간의 정체를 알면 대응할 수 있습니다.

    약 20분가장 실전적

    왜 앞의 지시를 잊을까

    클로드는 대화 전체 — 주고받은 말, 읽은 파일, 명령 실행 결과 — 를 컨텍스트라는 기억창에 담아둡니다. 디버깅 한 번, 코드베이스 탐색 한 번으로도 수만 토큰이 들어찹니다. 그리고 이 창이 차오를수록 성능이 떨어집니다.

    업계에서는 이걸 컨텍스트 불안(context anxiety)이라고 부릅니다. 검증되지 않은 텍스트가 기억창을 오염시켜 판단이 흐려지는 현상입니다. 컨텍스트는 가장 중요한 자원입니다.

    명령언제 쓰나
    /clear다른 주제로 넘어갈 때. 대화를 완전히 초기화합니다. 가장 자주 씁니다.
    /compact같은 작업이 길어졌을 때 요약해서 압축. /compact API 변경에 집중해줘 처럼 방향도 줄 수 있습니다.
    /context지금 무엇이 얼마나 차 있는지 확인.
    /btw대화 기록에 남기지 않고 곁가지 질문. 답이 컨텍스트를 차지하지 않습니다.
    Esc진행 중인 작업 중단. 맥락은 유지됩니다.
    Esc Esc
    /rewind    		이전 시점으로 복원. 대화만 / 코드만 / 둘 다 중에 고릅니다.
    되돌려줘명령어가 아니라 그냥 말. 방금 한 변경을 취소합니다.
    하나만 기억한다면

    같은 문제로 두 번 고쳤는데 아직도 틀리면, 세 번째 수정을 시도하지 마세요. 그 시점의 컨텍스트는 실패한 시도들로 오염돼 있습니다. /clear 하고, 그동안 알게 된 걸 반영한 새 프롬프트로 다시 시작하세요. 깨끗한 세션 + 좋은 프롬프트는 긴 세션 + 누적된 수정보다 거의 항상 낫습니다.

    체크포인트 — 과감하게 시도해도 되는 이유

    프롬프트를 보낼 때마다 체크포인트가 저장됩니다. 그래서 “일단 과감하게 해보고 아니면 되돌린다”는 전략이 가능합니다. 터미널을 닫았다 나중에 열어도 되돌릴 수 있습니다.

    약 25분피드백최우선

    왜 검사가 없으면 사람이 센서가 되는가

    클로드는 작업이 다 된 것처럼 보이면 멈춥니다. 돌려볼 검사가 없으면 “다 된 것 같다”가 유일한 신호이고, 그때부터 사람이 검증 루프가 됩니다. 모든 실수가 사람이 발견할 때까지 기다리는 상태죠. 이 실패 유형에는 이름도 있습니다 — 승리 선언 편향(victory declaration bias).

    검사를 주면 고리가 스스로 닫힙니다. 클로드가 작업하고, 검사를 돌리고, 결과를 읽고, 통과할 때까지 반복합니다.

    단계 1 · 프롬프트에 검사를 넣는다

    가장 가벼운 방법이고 오늘 당장 됩니다. 05단계 원칙 2가 이겁니다.

    ▷ 프롬프트 안에서 고리 닫기
    장바구니 합계 계산 함수를 만들어줘.

검증 기준:
- 빈 장바구니는 0
- 수량 2개짜리 1000원 상품은 2000원
- 10% 쿠폰이 붙으면 1800원
- 수량이 음수면 오류를 던진다

만든 다음 테스트를 돌리고, 실패하면 통과할 때까지 고쳐줘.
마지막에 테스트 출력 결과를 그대로 보여줘.

    단계 2 · 세션 전체의 종료 조건을 건다

    /goal 로 조건을 걸어두면 매 턴이 끝날 때마다 별도의 평가자가 조건 충족 여부를 다시 확인하고, 해결될 때까지 클로드가 계속 일합니다.

    클로드 코드 안에서
    /goal 모든 테스트가 통과하고 타입 체크에 오류가 없을 것

    단계 3 · 훅으로 강제한다

    Stop 훅은 검사를 스크립트로 돌려서, 통과하지 못하면 턴이 끝나는 것 자체를 막습니다. 가장 결정적인 관문입니다. (11단계에서 훅 문법을 다룹니다.)

    단계 4 · 다른 눈으로 본다

    여기서부터 추론형 센서입니다. 자기가 쓴 코드를 자기가 채점하지 않게 만드는 방법입니다.

    /code-review

    훅과 권한 — 요청이 아니라 강제

    약 25분가드레일설정 파일 편집

    권한 모드 — 첫 번째 가드레일

    모드동작
    자동 (auto)별도의 분류 모델이 사람 대신 행동을 검토합니다. 권한을 넘어서는 시도, 알 수 없는 인프라 접근, 외부 콘텐츠에 이끌린 행동만 막고 나머지는 묻지 않습니다. Pro·Max·Team의 터미널·VS Code 세션 기본값.
    수동 (Manual)파일 쓰기, 명령 실행, MCP 도구 사용 전에 매번 물어봅니다. 그 외 요금제의 기본값.
    플랜 (plan)읽기만 하고 아무것도 바꾸지 않습니다.

    Shift+Tab 으로 전환합니다. 입문자는 처음 몇 주 수동 모드를 권합니다 — 클로드가 어떤 명령을 실행하려는지 눈에 익히는 시간이 나중에 큰 자산이 됩니다.

    익숙해지면 매번 승인하는 대신 범위를 정해두세요.

    • /permissions — 안전한 도구를 미리 허용 (npm run lint, git commit 등)
    • /sandbox — OS 수준에서 파일·네트워크 접근을 제한한 채 자유롭게 작업하게 함

    훅 — 무조건 매번 일어나는 일

    훅은 클로드 코드가 특정 시점에 자동으로 실행하는 명령입니다. 클로드가 판단할 여지가 없습니다. 자주 쓰는 시점은 넷입니다.

    시점언제 터지나주로
    PreToolUse도구 실행 직전. 막을 수 있음위험한 파일 수정 · 명령 차단
    PostToolUse도구 실행 성공 후포맷팅, 린트, 자동 빌드
    Stop클로드가 응답을 마칠 때검사 통과 전까지 종료 차단
    Notification클로드가 입력을 기다릴 때데스크톱 알림

    가장 쓸모 있는 첫 훅 — 편집할 때마다 포맷

    .claude/settings.json

    두 번째 훅 — 건드리면 안 되는 파일 차단

    .env, 잠금 파일, .git/ 같은 곳을 지킵니다. 스크립트가 종료 코드 2로 끝나면 클로드 코드가 편집을 막고, 왜 막혔는지 이유를 클로드에게 전달해서 방법을 바꾸게 합니다.

    .claude/hooks/protect-files.sh
    #!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
FILE_PATH="${FILE_PATH//\\//}"

PROTECTED=(".env" "package-lock.json" ".git/")

for p in "${PROTECTED[@]}"; do
  if [[ "$FILE_PATH" == *"$p"* ]]; then
    echo "차단: $FILE_PATH 는 보호된 파일입니다 ($p)" >&2
    exit 2
  fi
done
exit 0

    직접 안 짜도 됩니다

    훅은 클로드에게 시키면 만들어 줍니다. 파일을 수정할 때마다 eslint를 돌리는 훅을 써줘 또는 migrations 폴더 수정을 막는 훅을 써줘 처럼요. 다만 무엇을 강제할지 정하는 건 사람의 몫입니다.

    훅 설계 두 가지 원칙

    1. 성공은 조용히, 실패는 시끄럽게. 통과했을 때는 아무 말도 하지 마세요. 컨텍스트만 잡아먹습니다. 실패했을 때는 오류 텍스트를 그대로 뱉으세요 — 그게 클로드에게 되먹임되어 스스로 고치는 재료가 됩니다.
    2. 규칙은 벌어들이는 것. 겪은 사고에 대해서만 훅을 만드세요. 각 훅이 어떤 사고를 막는지 설명할 수 없다면 그건 잡음입니다.

    CLAUDE.md의 “.env를 절대 수정하지 마”는 요청입니다. PreToolUse 훅으로 그 편집을 막는 건 강제입니다. 반드시 지켜져야 하는 규칙이라면 훅으로 만드세요.

    스킬 — 가끔 필요한 지식과 절차

    CLAUDE.md는 매 대화에 통째로 올라갑니다. 그래서 가끔만 쓰는 내용은 여기 넣으면 안 됩니다. 스킬은 필요할 때만 불러오기 때문에 평소엔 이름과 한 줄 설명만 차지합니다.

name: api-conventions
description: 우리 서비스의 REST API 설계 규칙
---
# API 규칙
- URL 경로는 kebab-case
- JSON 속성은 camelCase
- 목록 응답에는 반드시 페이지네이션을 넣는다
- 버전은 경로에 표시한다 (/v1/, /v2/)

name: fix-issue
description: GitHub 이슈 하나를 처리한다
disable-model-invocation: true
---
$ARGUMENTS 이슈를 분석하고 고쳐줘.

1. gh issue view 로 이슈 내용을 본다
2. 관련 코드를 찾는다
3. 고친다
4. 테스트를 쓰고 돌려서 확인한다

6. 설명이 담긴 메시지로 커밋하고 PR을 연다
